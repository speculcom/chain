Credentials

ERC-6551：给每个 NFT 一个链上账户 / ERC-6551: token-bound accounts

The intersection: ERC-6551 derives a deterministic smart-contract account for every NFT, so the NFT can hold assets and call applications without changing the existing NFT contract. For agents this means identity-as-account: an NFT representing an agent or character can own a wallet, permissions and assets, and transferring the NFT transfers control.
Scope: the registry uses create2 for predictable addresses, accounts are ERC-1167 minimal proxies to an implementation, and the execution interface lets valid signers call CALL/DELEGATECALL/CREATE/CREATE2 on the account’s behalf.
Open: account security depends on the implementation and signer policy; it does not solve key management, social recovery or permission revocation; it is not a general agent-identity standard, and cross-chain/account-abstraction combinations remain fragmented.

Safe 智能账户：多签、阈值与账户抽象 / Safe smart account: multisig, threshold and account abstraction

The intersection: turning an account from a key pair into a contract — Safe is multisig at its core, defining a set of owners and a threshold that must confirm a transaction before execution; owners can be EOAs, other smart accounts or even passkeys.
Scope: the docs also cover modules (allowance, recovery, 4337, passkey), guards, batched transactions and the singleton/proxy architecture, which makes “give an agent a capped, revocable account” engineering-feasible.
Open: modules and guards are security-critical, and the docs state a malicious guard can block transactions and lock funds; multisig reduces single-key risk but does not remove key management, social engineering or module bugs, so institutional use needs its own audit.

W3C 去中心化标识符 DID / W3C Decentralized Identifiers (DID)

The intersection: a resolvable identifier for an agent, device or dataset, whose DID document carries public keys and service endpoints, so control of the identifier can be proven without asking a registry for permission. Scope: the specification defines syntax, data model, core properties and resolution only; it presupposes no particular technology or cryptography, and it does not warrant that assertions in the document are true — the authors state that an alsoKnownAs assertion does not prove itself and requires independent verification by the requesting party. Open: revocation is not expressed through verification relationships and is left to each DID method, interoperability across methods is not guaranteed, and "control provable without permission" does not mean discovery and resolution are independent of third parties.

W3C 可验证凭证 / W3C Verifiable Credentials

The intersection: expressing "some body attested this model, dataset or person" as a machine-verifiable credential, so a verifier need not call back to the issuer. Scope: the specification says it twice — verifiability does not imply the truth of the claims, and verification does not evaluate that truth; whether to rely on it is a separate step the verifier performs under its own rules, which the spec calls validation and places outside its scope. Open: revocation and status checking, and the choice of trust anchor, depend on the implementation, and the specification supplies a data model rather than shared field semantics.

Akash Network：反向竞价的去中心化算力市场 / Akash Network: a reverse-auction marketplace for compute

The intersection: turning GPU and container compute into a public order book — users declare CPU, memory, storage and GPU needs in YAML (SDL), independent providers worldwide bid, users choose on price, location and reputation, and pay per block with the ability to close at any time.
Scope: the official docs state it runs Docker containers, including model training, inference servers, Jupyter and LLMs/diffusion models; payment uses the USD-pegged ACT credit or AKT.
Open: “up to 85% cheaper” is vendor marketing, not a price this site audited; provider SLA, data residency, network bandwidth and failure recovery are not uniformly guaranteed, so production use needs its own due diligence and load testing.

ACP：让 AI Agent 走完商家结账 / ACP: agent-ready merchant checkout

The intersection: ACP does not decide how a model thinks; it turns agent shopping into merchant-implementable checkout interfaces — product feed, cart, checkout session, fulfillment options, delegated payment, delegated authentication, orders and webhooks. The merchant remains merchant of record and can accept or decline per agent or per transaction; payment credentials move through a payment handler without exposing the underlying card.
Scope: positioned as an open standard under Apache-2.0, with REST and MCP integration; Stripe’s Shared Payment Token is the first compatible delegated-payment implementation, and OpenAI’s ChatGPT Instant Checkout is the first live surface.
Open: the spec is beta with limited merchant and geographic coverage; refunds, disputes, fraud and compliance remain with merchants and PSPs; it is not x402-style per-call API billing — the two solve different layers.

AP2：Agent Payments Protocol / AP2: Agent Payments Protocol

Problem: when an agent pays on a user’s behalf, how does the merchant know the user really authorised it, and what evidence exists if disputed? AP2 records the scope of authorisation in signable, selectively disclosable mandates rather than passing a card number.
Where the evidence sits: Google’s 2026-04-28 post donates AP2 to the FIDO Alliance and releases v0.2 with Human Not Present; the official FAQ says AP2 is payment-agnostic and defines Checkout / Payment mandates, each open or closed; Protofire’s October 2026 comparison states no public, confirmed production AP2 transaction was found.
Limits: no publicly confirmed production transaction as of October 2026; v0.2 is only the second release and replaced the earlier mandate model; AP2 does no checkout, catalogue or settlement and must sit inside UCP or another commerce protocol; the repo is still under Google’s org while FIDO stewardship begins.
What it does not claim: a payment network already at scale; a crypto-only protocol; a replacement for card networks or acquirers; unconditional agent charging — Human Not Present still depends on pre-authorisation.

Arbitrum Nitro：乐观汇总与交互式欺诈证明 / Arbitrum Nitro: optimistic rollup with interactive fraud proofs

The intersection: an L2 moves execution off-chain and posts data and results back to L1; Nitro rests on four ideas — sequencing then deterministic execution, Geth at the core, separating execution from proving, and an optimistic rollup with interactive fraud proofs.
Scope: the docs describe the sequencer ordering transactions and giving immediate results, a batch poster sending compressed batches to Ethereum as EIP-4844 blobs or calldata, and an L1 data fee covering that cost; AnyTrust trades a weaker trust assumption (a data availability committee) for lower fees and falls back to rollup if the committee fails.
Open: the sequencer is a centralised ordering point with, in the docs’ words, limited power over ordering; withdrawal challenge periods, sequencer downtime and MEV depend on each chain’s configuration, and this site does not rank L2 safety.

DID Resolution：把标识解析成可核验文档 / DID Resolution: resolving identifiers into verifiable documents

The intersection: AI content credentials and model provenance statements often use DIDs for issuers or subjects; verifiers must resolve the identifier into a DID document and metadata to find verification methods and status information.
Scope: the specification defines DID resolution as obtaining a DID document and accompanying metadata, and requires conforming resolvers to implement the resolution function for at least one DID method and return a DID document. ERC-1271：合约账户签名验证 / ERC-1271: Standard Signature Validation Method for Contracts

The intersection: when an AI content credential or data permission is signed by a contract account rather than a personal private key, verifiers need to ask whether the contract recognises the signature; ERC-1271 provides a common contract-side validation entry point.
Scope: the abstract says EOAs can sign messages with private keys but contracts cannot, and proposes validation through isValidSignature(hash, signature) on the signing contract. It standardises the interface, not the internal decision logic, and does not make the underlying business claim true.
Open: contract wallets, multisigs and permission modules implement their own validation, so applications still need to check implementation and upgrade risk; the specification moved from the EIPs repository to ERCs and is Final, but this site does not infer support by every contract account.

EIP-4844：Shard Blob Transactions / EIP-4844: Shard Blob Transactions

Intersection: AI training data, model cards and content credentials need a low-cost data-availability layer; blobs put bulk data into consensus-layer sidecars while the execution layer sees only commitments — useful for verifiable records that should not enter the EVM.
Scope: the official spec frames this as a stop-gap before full sharding; blob data is downloaded and briefly retained by consensus nodes, cannot be read directly by EVM execution, and is capped per block with a separate fee market.

EIP-712：类型化结构化数据哈希与签名 / EIP-712: Typed Structured Data Hashing and Signing

The intersection: AI content credentials, model provenance and permission statements often need an offline signature over a structured claim; EIP-712 specifies how typed data is encoded, hashed and included in signable messages instead of treating complex claims as opaque byte strings.
Scope: the abstract describes a standard for hashing and signing typed structured data, and the motivation warns that errors in structured hashing lose security properties; the text also says it does not include replay protection. Open: an AI credential system still has to define its schema, domain separation, replay protection and verifier trust; the EIP status is Final, but this site does not infer deployment on every chain or wallet.

ERC-4337：账户抽象（alt mempool） / ERC-4337: account abstraction (alt mempool)

Problem: an EOA’s validation rules are fixed by the protocol; a smart-contract wallet that wants custom signatures, batching or sponsored gas would need consensus changes. ERC-4337 avoids that with an alt mempool and an EntryPoint, turning user intent into a UserOperation.
Where the evidence sits: the EIP abstract defines UserOperation, a separate mempool, bundler packaging and the handleOps call; the official docs split roles into EntryPoint, Bundler and Paymaster, and note that a Paymaster can sponsor gas or accept ERC-20.
Limits: the alt mempool brings bundler centralisation and censorship risk; Paymaster sponsorship can be abused without reputation/limits; avoiding consensus changes leaves the base account model as EOA plus contract; EntryPoint versions (v0.6/0.7/0.8) need separate compatibility checks.
What it does not claim: a replacement for EIP-7702; a guarantee of gasless transactions (it moves who pays); the only account-abstraction route; that every wallet supports it.

ERC-8004：Trustless Agents / ERC-8004: Trustless Agents

Problem: why should an unknown agent be trusted? With no shared identity and no portable track record, every interaction is a blind leap. ERC-8004 separates identity, reputation and validation into three singleton registries so an agent can be checked before transacting.
Where the evidence sits: the official 8004 blog dates mainnet to 2026-01-29 and describes the three registries; Identity is ERC-721 plus an agent-card JSON (including A2A / MCP endpoints), Reputation stores client feedback, Validation plugs in TEE / zkML / staking re-execution; the blog states x402 payment integration. Taiko’s guide and the official FAQ confirm Draft status and a v2 in development.
Limits: Draft means interfaces may change; reputation can be sybil-attacked or farmed, and validation is pluggable rather than on by default; registration proves an entry exists, not capability or legality; cross-chain registrations are self-declared, not automatically verified.
What it does not claim: that on-chain equals trustworthy; a payment protocol; that every agent must register; a replacement for A2A or MCP.

The intersection: the minimal shared interface for fungible tokens — every unit is equivalent and divisible, suiting pricing, voting, staking and settlement; OpenZeppelin’s implementation packages name/symbol/decimals with transfer and allowance logic into an inheritable contract.
Scope: the docs stress that decimals is a display convention only and arithmetic on-chain stays integer; the default is 18 and can be overridden. This is directly relevant to agent payments and per-token billing.

Mastercard Agent Pay：卡组织的 Agent 支付框架 / Mastercard Agent Pay: a card-network framework for agents

The intersection: Agent Pay is not one API but four card-network pieces — Know Your Agent registration, an Agentic Token uniquely issued per agent, biometric authorisation through Mastercard Payment Passkeys, and Verifiable Intent binding the consumer’s original instruction to the final transaction. Tokens can be scoped by amount, merchant category, time window and purpose, and revoked at any time.
Scope: launched in the US in 2025 and completed live transactions in 2026 across Australia, New Zealand, Singapore, Malaysia, India, Korea, Taiwan and Latin America, with DBS/UOB, hoppa and Santander among participants. Open: it is not on-chain settlement and not a single universal standard; KYA and risk scoring remain with the network/issuer, cross-network interoperability with Visa TAP and Amex ACE is still evolving, and merchant upgrades and geographic coverage are uneven.

Visa TAP：让商家认出可信的购物 Agent / Visa TAP: letting merchants recognise trusted shopping agents

The intersection: TAP answers “how does a merchant know this agent is really consumer-authorised, not a malicious bot?” It adds payment semantics on top of Web Bot Auth HTTP Message Signatures: a signed request can distinguish browse from pay, bind the consumer behind the agent, and declare the expected payment method (network token, guest checkout or micropayment).

x402：用 HTTP 402 直接为 API 付费 / x402: paying for APIs over HTTP 402

The intersection: putting pay-per-call back into HTTP semantics — the server returns 402 plus payment instructions, the client pays, then receives the resource, with no accounts, sessions or credential management. Scope: the official docs describe a five-step flow (request, 402 instructions, payment payload, verification and settlement by the server or a facilitator, resource) and state that the standard itself has zero fees and supports batched EVM settlement.
Open: finality, refunds, disputes and compliance sit with the specific service and on-chain asset, not the protocol layer; this entry does not judge any x402 service’s pricing or reliability.
