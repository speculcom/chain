Verification path: what to check on an AI-and-chain claim

The order is: identify the type first, go back to the specification text, then check rights and custody, and finally who can verify. Each step links only to entries verified here; no conclusions and no recommendations, and if the original text cannot be found the process stops at that step rather than filling in with a second-hand summary.

  1. 1. First establish which category the claim belongs to: provenance signalling, verifiable credentials, or a decentralised inference network — the three are checked differently. entry
  2. 2. For a content credential: establish the specification version and assertion types, and confirm which source type marks an AI output. entry
  3. 3. If a claim needs an offline signature: encode and hash typed structured data instead of treating a complex claim as an opaque byte string. entry
  4. 4. If the signature comes from a contract account: check the contract-side signature validation interface rather than verifying only as an EOA signature. entry
  5. 5. If the claim records who attested what under a schema: check schema registration and attestation contracts, and remember recording does not make the content automatically true. entry
  6. 6. For a dataset or model file: confirm it is content-addressed, so identical bytes yield an identical identifier on any node. entry
  7. 7. If provenance spans multiple files: check the data model and linking above CIDs, not only a single file hash. entry
  8. 8. Then ask who still holds it: the proof of custody is periodic and does not imply fast retrieval. entry
  9. 9. If the claim is that some body attested it: separate issuer, holder and verifier, and remember that verifiable does not mean true. entry
  10. 10. If control of an identifier is claimed: check verification methods and revocation in the DID document, noting that revocation rules are per method. entry
  11. 11. To turn an identifier into verifiable material: run DID resolution to obtain the document and metadata, then check the target method implementation. entry
  12. 12. If data usage is at issue: separate token-gated access from lawful usability — the latter is a legal judgement, not something a protocol answers. entry
  13. 13. If private data is used for training or evaluation: separate selling raw data from authorised compute, and check allowed algorithms, compute environment and result boundaries. entry
  14. 14. For decentralised inference: establish the role split and the scoring mechanism, since incentive distribution follows validator scores and subnets are not directly comparable. entry
